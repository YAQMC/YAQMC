# Application updates

> [简体中文](zh-CN/app-updates.md) | **English**

Settings → Updates checks official YAQMC GitHub Releases. Background checks start 30 seconds after launch and recur daily. They only notify. **Download, update and restart** downloads the selected package, verifies it, saves the playback queue, waits for plugin transactions, installs and restarts without another confirmation. Playback continues during download. Cancel is available until installation preparation begins.

## Supported installations

Official Windows NSIS installers and portable EXEs, and official Linux AppImages, support x64 and arm64 updates. Package managers, deb/rpm, tar archives, AUR, source builds and unknown distributions only notify; use the original distribution channel to update them. Android retains its existing release notification flow.

An optimized or packaged local build is still a source build. The desktop build embeds the source commit, tag, architecture and distribution identity. Only the official tagged release workflow marks a build as an official Release. Runtime environment variables cannot turn a local build into an official release. An existing historical executable must first be replaced with a release that contains this updater.

**Receive prereleases** is disabled by default and saved locally. Enabling it includes published beta/nightly and other valid SemVer prereleases. Disabling it never downgrades. Updates must have a strictly higher SemVer; a different commit at the same version does not trigger replacement. Drafts and unrelated Git branches are ignored.

## Using beta releases

Install an official release containing this updater once, open **Settings → Updates**,
enable **Receive prereleases**, then check for updates. A published higher version
such as `0.1.2-beta.2` is offered to a `0.1.2-beta.1` user. Click **Download, update
and restart** to apply it. Turning the switch off keeps the installed beta until a
higher stable version, such as `0.1.2`, is published. It does not return to `0.1.1`.

Packages downloaded from CI or **Build artifacts**, AUR and local Git builds only
notify; install an official Release package to use in-app replacement. Publishers
use version tags in **YAQMC release**, not raw branch artifacts. See the
[beta/nightly publishing guide](ci.md#publish-a-beta-or-nightly).

## Integrity and installation

The host fixes a release and asset identity, package format, application architecture, byte size and GitHub SHA-256 before downloading. It revalidates the release and hashes the downloaded file again before installation. Missing or changed assets stop the update. Requests use an isolated session and the system proxy without music-provider cookies or credentials. HTTPS redirects are limited to GitHub and its release asset hosts. Downloads stream to disk and partial files are removed after cancellation or failure.

NSIS updates use `electron-updater`, architecture-specific metadata and its SHA-512 verification. Configured publisher signature verification remains enabled. Current unsigned official packages rely on the official HTTPS distribution and checksums; those hashes are integrity checks, not an independent publisher signature.

Portable and AppImage updates use the native `yaqmc-update-helper`. It prepares a file beside the current executable, waits for the old process, retains a backup, replaces the original path, and starts the new application. A main-window/Core readiness acknowledgement commits the update. Startup failure triggers one file-level rollback and relaunch. Durable journals support interrupted-operation recovery. NSIS errors use the installer's recovery and retry behavior. These mechanisms do not downgrade user databases or reverse third-party service changes.

Application data, installed plugins, credentials, settings and queues retain their existing locations. Before quitting, Core blocks new plugin mutations and drains plugin commit/rollback transactions. A failed exit preparation leaves the application installed. Failed or cancelled downloads can be retried from Settings.

## Host interface

`host_updater_check`, `host_updater_status`, `host_updater_start`, `host_updater_cancel` and `host_updater_preferences` are typed, main-window-only host methods. The legacy download/install methods remain available. Start consumes a host-owned candidate ID; callers cannot submit a URL, executable path or command. Long operations return an operation ID and publish `host://update` progress. The settings page queries status after reconnecting. Plugin scripts, lyrics windows and local HTTP clients cannot start updates.

## Release overview

Future Release bodies are generated by `scripts/ci/release-commits.mjs`: short SHA, original commit subject and commit link, in commit order. Stable releases compare with the previous published stable ancestor. Prereleases use the previous published prerelease in the same version line, falling back to the previous stable ancestor. Initial releases include history from the repository root. Oversized bodies link to the complete `COMMITS.md` attachment. Download instructions remain in `DOWNLOADS.md`; licenses, copyright notices, corresponding source and package checksums remain release assets. Existing releases are not rewritten.

`scripts/ci/app-update-acceptance.mjs` builds separate QA application packages and profiles to exercise real package updates. Set `YAQMC_UPDATE_HELPER_BIN` to a compiled helper for that OS and architecture. Run Windows fixtures natively; Linux AppImage fixtures need a Linux desktop or virtual display with the Chromium sandbox available. The test uses synthetic session data and a local transport seam rather than publishing a production release.
