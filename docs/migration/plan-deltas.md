# Migration plan deltas

This record captures implementation facts discovered while executing the retained Electron migration plan. It does
not authorize a runtime migration outside the current task. The binding amendment and the provenance release gate
remain controlling requirements.

## Task 4: workspace and Core scaffold

- The current composition order in `src-tauri/src/lib.rs` is authoritative for later extraction and differs from the
  source plan's section 10.2. Today it applies the graphics policy; builds/configures Tauri and plugins; configures
  window/page ownership handlers; then, in setup, resolves paths, opens storage/plugins, initializes logging,
  credentials, QQ Music, audio, playback, queue restoration, local API, integrations, diagnostics, event forwarding,
  Tauri-managed state, and account restoration. No part of that order is moved by Task 4.
- The local API configuration is resolved as `app_config_dir()/local-api.json`, not from application data. Core must
  therefore receive `local_api_config_path` explicitly rather than deriving it from `data_dir`.
- The strict forms `tauri::async_runtime::spawn(` and `tauri::async_runtime::spawn_blocking(` occur 24 and 3 times,
  respectively. Later moves must classify Tauri-shim work separately from Tokio Core work; the remaining six
  unqualified `spawn_blocking` occurrences are not part of the strict Tauri count.
- `app_preferences.rs`, `platform.rs`, and `system_media.rs` are not currently Tauri-free.
- Player/audio/media/streaming and QQ Music/storage/credentials/local-API modules form coupled compile closures.
  Later extraction must retain a compilable closure or introduce an explicit shim/re-export; it must not move an
  arbitrary module in isolation.
- `src-tauri/build.rs` retains the 117-command `AppManifest`, and autogenerated permissions remain Tauri-shim
  responsibilities until the P2 registry work establishes the single registry source of truth.
- A root Cargo workspace changes Cargo's active output directory to root `target`. CI caches, package/staging
  consumers, active acceptance instructions, and release workflows use that directory while preserving target triples,
  release artifact names, and package behavior. Historical plans retain their historical paths.

The binding amendment's registry/cap rules, P12 human gate, P14 live-account gate, conditional reqwest policy,
Electron fuse policy, and Git cutover/rollback strategy apply to all later work. Task 4 implements none of the P2
registry or framing work, payload caps, P12/P14 test gates, provider transport or qm-api-rs integration, Electron
code, Git cutover, backup branch, tag, merge, push, or default-branch action.
